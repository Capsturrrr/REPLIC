METHOD CORRECTION 2026-10-11: runs 1-3 used `netem ... rate R limit 60`. In netem the limit counts packets sitting in the delay line, so on the satellite path (about 200 packets in flight) any window above ~60 overflowed the qdisc. That explains the 60-100 retransmissions per transfer (13-20%) for the tuned AIMD and neural senders, which my first guess blamed on reordering. Runs 1-3 therefore overstate loss for large windows on high-delay paths, and the satellite result (and TCP comparison) is not representative of the simulated 'sat' path.
netem_full.sh now puts delay/jitter/loss/reorder in netem (limit 100000) and the bottleneck in a separate tbf stage with a drop-tail queue of 50-100 packets, matching the simulator. Re-run needed.
Simulator fix: the virtual-time queue delivered strictly in send order, so --reorder 1 had no effect; it now delivers by arrival time. Default (in-order) results unchanged: make repro geo-mean 0.534, faster on 89/100.
