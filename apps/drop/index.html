RUDP / Drop

Send a file across a bad network.

Your file travels over our own reliable-UDP protocol through an emulated link. Congestion-control policies take turns, and the receiver checks every byte against the original.

What is happening when you press send
  1. Handshake. The sender and receiver swap a SYN and a SYN-ACK so both agree on a starting point. Nothing is sent until this takes one round trip. On a lossy link a lost SYN-ACK costs a retry, a bug our tests found and fixed.
  2. Slow start. The sender begins with 10 packets in flight and doubles that every round trip, because it does not yet know how fast the link is. This ends at the first sign of trouble (a loss, or delay rising).
  3. Steady state. Now the policy decides how big the window should be. The window is how many 1200-byte packets may be unacknowledged at once. Too small wastes the link; too big overflows the router queue and packets are dropped. This is where the policies differ.
  4. Loss and recovery. The receiver reports what arrived with a SACK bitmap. A gap is repaired by a fast retransmit (resend just the missing packet). If no feedback arrives at all, the retransmission timer expires, the slow and costly path. Both show as ticks under each chart (amber: retransmit, red: timer expiry).
  5. Finish and check. After the last packet is acknowledged, the receiver closes with a FIN. We then hash the file it wrote and compare with the hash of what you sent. A match proves every byte arrived once, in order, unchanged.

HOW TO READ THE RESULTS

Goodput: useful file bytes per second, retransmissions excluded.
Retransmitted: packets sent again. More means more waste, not always a slower run.
Avg RTT: round trip time with queueing included. Above the link's base RTT means the router queue is filling.
Best possible: file packets divided by the link's packet rate, plus one RTT. No protocol can beat it.

The emulator (bin/impair) adds delay, jitter, random loss, a fixed packet rate and a drop-tail queue. It is a model, not a real network. Each policy runs once, so a gap of a few percent is noise.

Race

idle

Nothing has been sent yet. Choose a file and a network, then press send. Each policy gets its own lane and runs one after another, so they do not disturb each other.

Real C code throughout: the sender is librudp, the receiver is bin/server, and the network is bin/impair, a UDP proxy that adds delay, jitter, random loss and a drop-tail bottleneck. Kernel TCP is not in this race because it cannot pass through a UDP proxy; the netem results in the report cover that comparison. One run per policy, so treat small gaps as noise. The report’s numbers come from 30 paths per policy, not from this page.
